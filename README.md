# Local AI Agents with Claude as Orchestrator

An experiment in running local AI agents on a personal machine, using **Claude as the orchestrator** and a **local LLM (via Ollama) as the worker** for mechanical code generation tasks.

## What this is

This project explores a hybrid AI architecture where:

- **Claude** handles reasoning, planning, architecture decisions, and code review
- **A local LLM** (`qwen2.5-coder:14b`) handles boilerplate, repetitive code generation, and first-pass implementations — running fully offline, at zero API cost

The integration is done via a **custom MCP (Model Context Protocol) server** that exposes the local model as a native Claude Code tool. Claude can then call it directly during any coding session, without manual intervention.

## Why

Two motivations:

1. **Data privacy** — generated code never leaves the machine. No third-party API sees your codebase.
2. **Offline capability** — works without internet access once the model is downloaded.

> **Honest note on token savings**: empirical testing showed that using a local model does NOT reliably reduce Claude API costs for individual tasks. The orchestration overhead (Claude constructing prompts, reading responses) roughly offsets the savings from not generating code directly. See [`qa.md`](qa.md) for the measured data.

## Hardware requirements

Tested on:

| Spec | Value |
|------|-------|
| Chip | Apple M3 Pro |
| Memory | 18 GB unified |
| OS | macOS Sequoia |

The setup requires **Apple Silicon** (M1/M2/M3) for Metal GPU acceleration. On Intel Macs, inference will be significantly slower.

Minimum recommended: **16 GB unified memory** to run `qwen2.5-coder:14b` comfortably alongside macOS and other tools.

## Architecture

```
User
 └─> Claude Code (Orchestrator)
       ├─> Reasons, plans, reviews code
       └─> Calls ollama_generate / ollama_chat  ← MCP tool (local, free)
             └─> qwen2.5-coder:14b (Ollama)
                   └─> Generates boilerplate, stubs, repetitive code
```

Claude decides when to delegate based on rules defined in `CLAUDE.md`. The local model handles self-contained, mechanical tasks. Complex or cross-file reasoning stays with Claude.

## Quick start

### 1. Install Ollama (ARM native)

Download from [ollama.com](https://ollama.com) — do **not** use Homebrew on Apple Silicon if your Homebrew is installed at `/usr/local` (Intel). That will install an x86_64 binary running under Rosetta with no GPU acceleration.

```bash
# Verify you have the ARM native binary after installing
file $(which ollama)
# Should show: Mach-O universal binary with 2 architectures: [...] arm64
```

### 2. Pull the model

```bash
ollama pull qwen2.5-coder:14b
```

~9 GB download. Smoke test:

```bash
curl -s http://localhost:11434/api/generate \
  -d '{"model":"qwen2.5-coder:14b","prompt":"Write a Python hello world","stream":false}' \
  | jq -r '.response'
```

### 3. Set context window

Ollama's default context window is 2048 tokens — too small for real code tasks. Always override:

```bash
# Create a Modelfile
echo "FROM qwen2.5-coder:14b
PARAMETER num_ctx 8192" > Modelfile

ollama create qwen2.5-coder:14b-ctx8k -f Modelfile
```

### 4. Set up the MCP server

```bash
# Install dependencies
pip install mcp httpx

# Register with Claude Code
claude mcp add ollama -- python /path/to/mcp_server.py
```

### 5. Add delegation rules to CLAUDE.md

```markdown
## Local agent delegation

You have access to an `ollama_generate` tool that runs a local model on this machine.

Use it for: boilerplate, test stubs, repetitive patterns, first-pass implementations from a spec.
Do NOT use it for: multi-file reasoning, debugging complex bugs, architecture decisions.

Default model: `qwen2.5-coder:14b-ctx8k`.
Always review and validate the output before integrating it.
If the output is wrong after two attempts, handle the task yourself.
```

## Key findings

### On token costs

Local model delegation is **not** a reliable token-saving strategy for individual tasks:

- With Bash+curl (1 round, happy path): **+37% more expensive** than Claude alone
- With MCP (1 round, happy path): **+18% more expensive** than Claude alone
- With correction rounds: costs compound quickly

The value is in **privacy and offline capability**, not cost reduction.

### On model quality

`qwen2.5-coder:14b` works well for well-known libraries and generic Python/JS patterns. It struggles with niche or SDK-specific APIs (e.g. the MCP Python SDK) that are underrepresented in its training data. In the E2E test, it required 3 rounds to produce correct MCP server code.

**Rule of thumb**: delegate tasks involving `stdlib`, common frameworks (`FastAPI`, `pytest`, `SQLAlchemy`), and repetitive patterns. Keep tasks involving internal APIs or obscure SDKs with Claude.

### On Ollama performance (M3 Pro, 18 GB)

| Condition | Throughput |
|-----------|------------|
| Cold start (model loading) | ~5 tok/sec |
| Warm (model in memory) | ~13 tok/sec |
| Expected range | 15–25 tok/sec |

Performance is within the expected range for `qwen2.5-coder:14b` Q4_K_M on Apple Silicon.
